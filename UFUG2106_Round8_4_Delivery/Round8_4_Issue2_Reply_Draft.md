Thanks for the detailed reproducer and the integration measurements. Your observations are useful, and I checked the individual items against our later standalone versions.

1. **RAM / optional candidate allocations:** The frozen `Round5.1` source has **not** been modified, so the original `orig(N)` / `cur(N)` allocation concern is still valid for that historical file. In the later standalone `Round8.2.1+` code we added positive-`ram_limit` parsing, a lower-memory fallback with bounded BDD construction, and an early stop once a feasible zero-area, zero-delay circuit is found. Direct tests on 20-input cases show much smaller peak RSS and valid output, but this is **not yet proof of a fix in the integrated Stage 2 solver**. Also, the general full-BDD path still has substantial row-buffer allocations.

2. **Official RAM evaluator discrepancy:** Our 9,000-KiB stress test is still marked `MEMORY_LIMIT` by the supplied evaluator even when using a tiny C program with very low current-image RSS. We have isolated this discrepancy and kept the evidence; we have not proved its implementation-level cause. The TAs have now clarified that **none of the 50 public or 50 hidden grading cases will set a `ram_limit`**, so we will retain the memory safety work without treating that particular cap as a final-grading blocker.

3. **BDD search budget in the integrated solver:** This is **not yet verified or addressed in our standalone integration**. Your controlled change from area 99,068 to 93,786 is worth preserving as an ablation result, with the caveat that target delay and runtime settings were modified. We should evaluate how to return unused budget to the BDD search while keeping end-to-end timing safe on the actual released banks.

4. **Fresh-checkout reproducibility:** Our recent research deliveries have reproducible source snapshots, but their experiment scripts still refer to earlier frozen delivery folders and the local evaluator/data banks. We still need a self-contained, documented final Stage 2 source/build package and a genuine clean-checkout test.

I suggest keeping this issue open until the resource checks have been reviewed **in the integrated solver**, the budget policy is tested, and the final source can be built reproducibly. Thanks again for raising the points; they uncovered gaps that the ordinary 50-case public regression did not reveal.
